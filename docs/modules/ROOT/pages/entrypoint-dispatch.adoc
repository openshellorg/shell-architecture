= Shell pains
:navtitle: Shell pains
:description: When the wrong Node or SDK runs, native modules break and tutorials blame you. Projects can pin versions—but the command you type still uses whatever is on PATH unless something dispatches to the right one.

You clone a repo, run `pnpm install`, and everything looks fine until you hit `node` or start the dev server. The wrong major is running. Native addons were compiled for a different ABI and now explode with errors that sound like *you* broke something. Someone on Slack says “just `nvm use` and rebuild better-sqlite3.” You were not careless. The shell simply started the wrong program.

That failure is common, predictable, and fixable at the boundary where a command becomes a process. This page explains what should happen there—and how OpenShellOrg’s work fits next to DevCentr’s broader toolchain docs.

== Pins on paper, wrong binary on PATH

Teams and ecosystems already *declare* what they need:

* `engines.node` in `package.json`
* `.node-version` or `.nvmrc`
* SDK channel pins (“use Flutter 3.x”), and similar files

Those declarations are useful. They tell humans and tools what the project expects. They do **not**, by themselves, change which executable runs when you type `node`, open the IDE’s integrated terminal, or double-click a script.

Soft warnings (`EBADENGINE`) arrive after the damage is done. Rebuild folklore treats the symptom after the wrong binary already compiled native code. A pin that nothing enforces is worse than no pin—it looks like a promise and behaves like decoration.

== What should happen when you press Enter

Imagine a small set of steps that run automatically for *this* command only:

. Read the project’s required version (from `engines`, a pin file, or equivalent).
. If that version is not installed yet, fetch it through a known manager or installer.
. Start **the same command again** under that version, for this process tree only.
. Leave the machine’s default toolchain alone—you should not have to “switch globals” just to open an old repo.

In this docs set we call the program that actually starts when you type a command the **entrypoint** (`node`, your shell, an SDK launcher, and so on). **Dispatch** is the work of picking (and if needed installing) the right version, then re-running the entrypoint so the right binary handles *this* invocation.

When dispatch works, opening a pinned project does not require a ritual of `nvm use`, manual PATH edits, or rebuilding native modules because the wrong Node ran first.

The system default may stay on “latest.” A hard error should be the **last resort**—when install or re-run is impossible (no network, policy block, no manager registered). The bar we aim for is **install if needed, then run**, not “stop and lecture.”

== Why “run nvm use when you cd” is not enough

Shell hooks that switch versions on `cd` help some people, sometimes. They are easy to miss:

* **IDEs and GUIs** often launch tools by absolute path, bypassing the shell profile that ran `nvm use`.
* **CI images** start clean; they need the same dispatch story, not a forgotten hook.
* **New teammates** should not have to join a particular shell “priesthood” before `node` tells the truth.

Dispatch belongs at the **entrypoint**—the binary or wrapper your OS actually executes—not only in optional shell configuration.

== A worked example: wrong shell host

OpenShellOrg’s https://github.com/openshellorg/nu-require[`nu-require`] applies the same pattern to **host shell** mismatch: if the project expects Nushell and you invoked something else, it can offer to install Nushell and **re-launch** under it. Toolchain version mismatch at `node` or an SDK launcher is the same idea with a different pin source.

== How this relates to DevCentr

**DevCentr** writes for teams and environments: how you pin toolchains, check health, repair broken installs, and plan upgrades over time. Their link:https://docs.devcentr.org/general-knowledge/explanation/infrastructure/toolchain-management.html[Toolchain Management Pattern] is the long-form philosophy; the link:https://docs.devcentr.org/general-knowledge/explanation/infrastructure/toolchain-control-plane.html[Toolchain Control Plane] essay describes the control-plane shape in more detail.

**OpenShellOrg** focuses on the moment you hit Enter in a shell or CLI: the invoked program should be the right host and version, or it should fetch what is missing and try again—without rewriting your global defaults.

The two doc sets are siblings, not competing rulebooks. Read both when you care about “always the right toolchain”; start here when the pain is “I typed the command and the wrong thing ran.”

== If you ship a version pin

Short checklist for CLI and runtime authors—not a substitute for the diagrams above, but a sanity pass before you publish:

* [ ] If you document a pin file or `engines`-style field, the default **entrypoint** installs (when needed) and re-runs under that version for the current command.
* [ ] Global defaults may stay on “latest”; one project must not require mutating the whole machine.
* [ ] Absolute-path and IDE launches get the same behavior as an interactive terminal.
* [ ] Show progress: which pin was read, what is downloading, which version is actually running.
* [ ] If you must fail hard, say which pin source blocked you—not “rebuild the native module.”
